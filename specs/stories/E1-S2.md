## User Story
As a user, I want Audit trail so that the milestone advances.

## Business Value
A lender's underwriting decisions and overrides must be reconstructible after the fact; the audit row is the only record of who did what and when.

## Description
Audit trail

## Scope
**In:** append-only audit_log table with actor, role, action, entity, correlation_id; the nine audited actions (POLICY_CREATED, POLICY_APPROVED, DOCUMENT_VERIFIED, DOCUMENT_REJECTED, REVIEW_APPROVED, REVIEW_REJECTED, DECISION_OVERRIDDEN, DISBURSEMENT_RECORDED, EOD_RUN); GET /api/audit filtered by entity_type/entity_id, ADMIN only; a database trigger that aborts UPDATE/DELETE on audit_log
**Out:** automated-decision logging (not an underwriter action); customer action logging

## Acceptance Criteria
- **E1-S2-AC1** — *Given* UNDERWRITER user 3 performing an audited action on application 7, *when* it succeeds, *then* one audit_log row has actor_user_id 3, actor_role UNDERWRITER, entity_type application, entity_id 7, a UTC occurred_at, and correlation_id equal to the response header.
- **E1-S2-AC2** — *Given* an existing audit row, *when* any UPDATE or DELETE runs on audit_log, *then* the database aborts and the row is unchanged.
- **E1-S2-AC3** — *Given* 3 audit rows for application 7 and 2 for application 8, *when* ADMIN GETs /api/audit?entity_type=application&entity_id=7, *then* exactly 3 rows return in ascending id order.
- **E1-S2-AC4** — *Given* an audited action that fails with a 409, *when* the request ends, *then* no audit row exists for it, because the audit write shares the action's transaction.
